ITEM 2 — the streaming usage window
────────────────────────────────────────────────────────────────────────

  The open question going in: `recordAIUsage` stamps `requestId` from the
  AsyncLocalStorage store *at emission time*
  (aiden-logging/dist/index.js:51-58), and for a stream the usage record
  is emitted from inside the ReadableStream, after the handler has
  already returned its Response. If the store were gone by then,
  `requestId` would be undefined, the sink could not correlate, and the
  row would be dropped.

  It is not gone. `createAIStreamResponse` constructs the stream inside
  the handler — therefore inside `withRequestContext`'s run — and async
  continuations scheduled from there inherit the store even after run()
  returns.

  ai_usage after the draft:

   route                        | model            | prompt | compl | cost_usd | org_id
  ------------------------------+------------------+--------+-------+----------+----------
   POST /api/tickets            | claude-haiku-4-5 |    247 |    35 | 0.000338 | org_acme
   POST /api/tickets            | claude-haiku-4-5 |    263 |    35 | 0.000350 | org_acme
   POST /api/tickets/[id]/draft | claude-haiku-4-5 |    413 |    97 | 0.000718 | org_acme   <- new

  PASS, and it settles F3 on the streaming path: with Anthropic the
  streamed call reports REAL counts, not zero. 413 prompt / 97 completion
  tokens, matching the usage block in the SSE `event: done` frame exactly.
  The estimated-usage fallback the v1 plan contemplated remains correctly
  out of scope.

  The OpenAI streaming gap is unchanged and untested here — that adapter
  never sets `stream_options: { include_usage: true }`, so a streamed
  call on OpenAI would report zero. That is the row to show and explain
  during the provider-switch demonstration.

  Window management: `beginAICall` is called before the stream is
  consumed and `endAICall` from both `onDone` and `onError`.
  `withAIUsageContext` is deliberately not used on this route — it closes
  on promise resolution, which for a stream is long before the record is
  emitted. Ordering inside `createAIStreamResponse` makes this safe: it
  calls `finalResponse()` (which reaches the sink) at line 81 and
  `onDone` at line 85, and the sink reads the correlation map
  synchronously before its first await.

  ai.draft in audit_logs:

   event    | resource_id | metadata
  ----------+-------------+-----------------------------------------------------------------------
   ai.draft | tkt_acme_6  | {"tone": "neutral", "model": "claude-haiku-4-5", "orgId": "org_acme"}

  Metadata is exactly what Dimension 6 specifies. No ticket content, no
  prompt, no draft text.

ITEM 6 — graded probe 6: a viewer is denied the draft route
────────────────────────────────────────────────────────────────────────

  Sign in as viewer@acme.test (org role "viewer" in org_acme) -> 302

  POST /api/tickets/tkt_acme_6/draft
    -> HTTP 403   {"error":"Forbidden"}

  Control, to show the 403 is a role denial and not an ownership one:

  GET /api/tickets/tkt_acme_6
    -> HTTP 200

  The viewer can read the ticket and cannot draft on it. That is the
  intended shape: the ownership step degenerates to a presence check for
  viewers, so it passes, and `assertCan("ticket.draft")` is what denies —
  403 rather than 404. A 403 leaks nothing here, because the caller is
  already authorised to see that the row exists.

  Auto-emitted denial event:

   event                   | metadata
  -------------------------+------------------------------------------------------
   security.ability_denied | {"action": "ticket.draft", "actorRoles": ["member"]}

  Note `actorRoles: ["member"]` — that is the caller's *global* NextAuth
  role, not the org role ("viewer") that actually decided the denial. The
  SDK emits this from inside `withAuth` and can only see what is on the
  session. This is a further edge of plan finding F9: auto-emitted denial
  events are not only missing `orgId`, they also record the wrong role
  vocabulary for an app whose authorization lives in Membership. Worth
  adding to the upstream report; the admin audit viewer must not present
  `actorRoles` as if it explained the denial.
