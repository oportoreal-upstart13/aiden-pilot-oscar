DIAGNOSIS OF THE TWO SMOKE FAILURES — recorded before any fix
════════════════════════════════════════════════════════════════

Both failures are defects in scripts/smoke.sh. Neither is a defect in
the application, and both were confirmed by reproducing them by hand
rather than inferred from the output.

────────────────────────────────────────────────────────────────
Probe 8 — "1 ticket(s) appear in both organizations"
────────────────────────────────────────────────────────────────

  Reported: before=[tkt_acme_5] after=[tkt_acme_5]

  The two lists are not overlapping. They are *identical*, because the
  organization never changed: the consultant was still in Acme for the
  second read.

  Root cause: the script's `status()` and `body()` helpers pass
  `curl -b "$jar"` but not `-c "$jar"`, so cookies the server sets during
  the run are read from the jar and never written back to it. The switch
  route's `Set-Cookie: deskline_org=org_globex` was therefore discarded
  by curl, and the follow-up list request carried the old cookie.

  Reproduced by hand:

    switch WITHOUT -c  -> HTTP 200, jar does NOT contain deskline_org
    switch WITH    -c  -> HTTP 200, jar contains: deskline_org  org_globex
    list after the cookie is kept:
      org_globex :: cmt39r4et0001mgdimlhcxh2l, tkt_globex_6, tkt_globex_5,
                    tkt_globex_4, tkt_globex_3, tkt_globex_2, tkt_globex_1

  So the application behaves exactly as the plan specifies — the switch
  works, and the list flips to a disjoint Globex set. The probe was
  asserting against a switch that, from the client's point of view, had
  never happened.

  Second, independent weakness in the same probe: the overlap check is
  `a.filter(x => x && b.includes(x)).length === 0`, which passes on two
  *empty* sets. Had the consultant owned no tickets in Acme, the probe
  would have reported PASS while testing nothing. A disjointness probe
  needs to assert that both sides are non-empty before it can mean
  anything — the same non-vacuity discipline probe 10 already applies.

────────────────────────────────────────────────────────────────
Probe 10 — "could not resolve the Globex agent's id"
────────────────────────────────────────────────────────────────

  The script reads the Globex agent's user id from `GET /api/me` as
  `.user.id`. That route returns the user object flat:

    {"id":"cmt344ymw000a1sdixu4fx61c","email":"agent1@globex.test",
     "name":"Farah Haddad","image":null,"emailVerified":null,
     "createdAt":"...","hasPassword":true,"accounts":[],
     "roles":[{"name":"member",…}]}

  There is no `user` wrapper, so `.user.id` was undefined and the guard
  correctly refused to run a vacuous check.

  This is precisely the failure mode `.claude/fixes/ui.md` already
  documents — "Never assume `{ items }`, `{ data }`, or
  `{ <resourceName> }`; read the exact `return NextResponse.json(...)`
  line first" — applied to a script instead of a component. The lesson
  was in the repository and was not followed.

  Note the guard did its job: rather than silently comparing against
  `undefined` and reporting PASS, it failed loudly and said the probe
  would be vacuous. The first assertion of probe 10 — no domain event
  from another organization, 43 entries, 35 attributed by actor — did
  pass on its own.
