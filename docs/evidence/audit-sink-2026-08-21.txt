6. TWO FAILURES OBSERVED — both open, neither fixed in phase 3
────────────────────────────────────────────────────────────────────────

6a. ai.classify is ABSENT. Triage returned null. Server log:

  {"level":40,"name":"DeskLine","requestId":"8debc289-...",
   "userId":"cmt344vlg00061sdiz4zhk5cr","model":"claude-haiku-4-5",
   "finishReason":"end_turn",
   "msg":"triage reply was not JSON; ticket ships unclassified"}

  Root cause, reproduced by calling the same prompt directly:

    RAW>>>```json
    {
      "priority": "medium",
      "category": "technical",
      "sentiment": "neutral"
    }
    ```<<<RAW
    parsed: undefined

  claude-haiku-4-5 wraps the object in a markdown code fence despite the
  system prompt stating "No prose, no explanation, no markdown code
  fence." `parsed` is undefined because the Anthropic adapter never sends
  responseSchema to the provider (F10), so triage.ts falls through to
  JSON.parse(text.trim()), which fails on the fence.

  The degradation path behaved exactly as designed: the ticket was still
  created, unclassified, the request still returned 201, and the failure
  was logged with metadata only. AI is an enhancement, not a gate.

  The same call also confirms F3 on the non-streaming path — Anthropic
  reported real usage: promptTokens 148, completionTokens 35,
  costUSD 0.0002584, latencyMs 1053.

6b. audit.auth.signin did NOT reach the table. It appears in the server
  log under the default sink:

  {"level":30,"name":"aiden:audit","event":"audit.auth.signin",
   "actorId":"cmt344vlg00061sdiz4zhk5cr",
   "metadata":{"provider":"credentials"},"msg":"audit.auth.signin"}

  /api/auth/[...nextauth] imports src/lib/auth.ts but not
  src/lib/security.ts, so the Prisma sink is not registered on the
  aiden-security instance that route resolves — and instrumentation.ts,
  which does import the sink, evidently registered it on a different
  instance. This is direct empirical confirmation of the plan's claim
  that a sink registered only from instrumentation.ts lands on an
  instance the handlers never see. The auth route needs the same
  side-effect import; that belongs to the Audit dimension in phase 4.

10. CLEANUP

  Both throwaway tickets were deleted; the seeded dataset is back to 12
  tickets. The audit_logs and ai_usage rows are kept as evidence — and
  their survival is itself the point: neither table holds a foreign key
  to Ticket, exactly so a usage or audit row outlives the row it
  describes.

  Still open after run 2: item 6b. `audit.auth.signin` continues to go to
  the default logger sink rather than the table, because
  /api/auth/[...nextauth] does not import src/lib/security.ts. The fix
  belongs to phase 4 and must import `@/lib/audit` directly from
  src/lib/auth.ts — routing it through src/lib/security.ts would be a
  cycle, since security.ts already imports auth.ts.
