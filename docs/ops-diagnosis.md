# Ops & Upgrade Diagnosis

## 1. Five reasons `aiden upgrade` can no-op

1. **Already on the latest version.** `aiden.config.ts`'s `version` field matches the latest published `@upstart13-com/aiden-*` single-train version — there's nothing newer to apply. Confirm: `npx @upstart13-com/aiden-cli upgrade --dry-run` reports zero pending changes, and the version in `aiden.config.ts` matches the packages' current published version in `package.json`.
2. **Dirty working tree.** Uncommitted changes are present, so the upgrade tool refuses to touch files it can't cleanly diff/revert if something goes wrong. Confirm: `git status` shows tracked changes; the upgrade CLI's own output names this explicitly before halting.
3. **Registry/network failure.** The CLI can't reach the npm registry to resolve the latest `@upstart13-com/aiden-*` versions (offline, registry outage, proxy/auth issue). Confirm: `npm ping` or `npm view @upstart13-com/aiden-cli version` fails/times out with the same network error the upgrade command surfaced.
4. **Scaffold codemods skipped due to customized anchor files.** A scaffold codemod fingerprints the file it would touch (e.g. `src/lib/security.ts`); if the fingerprint no longer matches the shipped default (because we've edited it — which we have, repeatedly, in this project), the codemod safely declines to overwrite rather than clobber local changes. Confirm: the upgrade's `ScaffoldReport` output lists the file as "skipped (customized)" rather than "applied" or "would apply."
5. **Unresolved `BREAKING.md` fix-up pending.** A prior upgrade left a manual fix-up step unresolved; `aiden doctor` surfaces it, and the upgrade halts until it's addressed. Confirm: `npx @upstart13-com/aiden-cli doctor` output names the specific `BREAKING.md` entry and package under a "pending manual fix-ups" section.

## 2. Recovery runbook for a bad/partial upgrade

- **Drop a bad upgrade commit:** `git reset --hard HEAD~1` — only safe if the upgrade was its own isolated commit (which `aiden upgrade` produces by design) and nothing else has been committed on top of it since.
- **Park in-flight changes before retrying:** `git stash` (or `git stash -u` to include untracked files) — use this instead of `reset --hard` when there's unrelated work-in-progress mixed in that shouldn't be discarded.
- **Hotfix-pin versions while investigating:** temporarily pin the affected `@upstart13-com/aiden-*` packages in `package.json` to the last known-good versions (`npm install @upstart13-com/aiden-x@<version>` for each), run `npm install`, verify the app is stable again, then return to `aiden upgrade` once the root cause is understood and fixed upstream or worked around. This is a stopgap, not a substitute for actually resolving the upgrade — the pin should come out once the real fix lands.

## 3. Duplicate-`aiden-logging` root cause: "request context empty in prod but works locally"

**Root cause:** `getRequestContext()` (used throughout `@upstart13-com/aiden-security` for `requestId`/`userId` auto-tagging, and directly by `src/lib/logger.ts`) is backed by a Node `AsyncLocalStorage` instance held as module-level state inside `@upstart13-com/aiden-logging`. If two copies of that package end up installed (a version mismatch between what the app depends on directly and what a transitive dependency pulls in, common when a dependency bumps its own `aiden-logging` peer range faster than the app does), each copy gets its **own separate `AsyncLocalStorage` store**. `withRequestContext()` (called by `withAuth`) writes into whichever copy the calling module resolved; `getRequestContext()` elsewhere may read from the *other* copy — which was never written to, so it returns an empty context. This is exactly the failure mode we independently ran into this session with the audit sink: two isolated module graphs (there, Turbopack dev-mode compilation boundaries rather than a duplicate install) each holding their own copy of `@upstart13-com/aiden-security`'s internal sink state — see `.claude/fixes/nextjs.md` for that specific incident. The duplicate-package version of this failure mode is the same root shape (module-instance state split across more than one copy of a package) with a different cause (bundler graph isolation vs. actual duplicate npm installs).

**Locally vs. prod is a bundling artifact, not an environment difference per se:** a local dev server and a fresh `npm install` in a clean CI/prod build resolve the dependency tree differently often enough (lockfile drift, a transitive dep bumping its `aiden-logging` peer range between the two installs) that one ends up with a single deduped copy and the other doesn't.

**Diagnose:** `npm ls @upstart13-com/aiden-logging` — if it prints more than one resolved version/location in the tree (npm nests a second copy under whichever dependency pulled in an incompatible range), that's the duplicate.

**Fix:** `npm dedupe` to collapse to a single shared copy where version ranges allow it; if a transitive dependency's declared range genuinely conflicts, add a package-manager `overrides` entry (npm) pinning `@upstart13-com/aiden-logging` to one version across the whole tree, then reinstall and re-run `npm ls @upstart13-com/aiden-logging` to confirm exactly one resolved copy.
