# UI & Frontend Fixes

- **[2026-02-10]** `{value && (<Component />)}` where value is `unknown` causes TypeScript error `Type 'unknown' is not assignable to type 'ReactNode'` → Use `{value !== null && (<Component />)}` to narrow the type, or cast/type-guard the value first.
- **[2026-02-10]** Hardcoded Tailwind colors (`bg-emerald-500`, `bg-red-500`, `bg-amber-500`) violate design system → Use CSS variable tokens: `bg-chart-2` (green/success), `bg-destructive` (red/danger), `bg-chart-3` (amber/warning). See `docs/design-system/01-foundations.md`.
  - **[2026-08-21] `[STRUCTURALLY PREVENTED]`** — but it was not, and the marker was lying. This entry claimed prevention by an ESLint `no-restricted-syntax` rule in `eslint.config.mjs`; that rule **did not exist** — the config was `nextVitals` + `nextTs` + `globalIgnores` and nothing else, so `npm run lint` passed happily on `bg-gray-500`. The claim was downgraded to an honest gap, then the gap was closed by writing the rule for real. It now bans `(bg|text|border|ring|fill|stroke|from|via|to|divide|outline|decoration|shadow|accent|caret|placeholder)-<tailwind palette>-<step>` in string literals **and** template literals, plus inline `style` attributes, across `src/**/*.{ts,tsx}`. Verified by probe: a file containing `className="bg-gray-500 text-zinc-400"`, a template literal with `border-slate-200`, and a `style={{…}}` produced three errors and exit 1; the probe was then deleted. **Known tension:** `05-data-display.md` shows a metric-card delta as `text-emerald-600 dark:text-emerald-400` and calls it "the ONLY place non-token colors appear" — the rule forbids that form. `02-components.md` renders the same card with `text-success`, which is the tokenised equivalent and passes. Use `text-success` / `text-destructive`; `05` needs correcting upstream.
- **[2026-02-10]** Calling `res.json()` twice on the same Response object throws "body already consumed" → Extract the JSON once into a variable and reuse it for both error checking and data extraction.
- **[2026-02-20]** UI fetch code assumed wrong API response shape, silently returning empty data
  - **Symptom**: UI selector always empty despite data existing. No error shown.
  - **Root cause**: Page assumed `{ items: [...] }` but route returned `{ data: [...] }`. The mismatch silently produced an empty array.
  - **Fix**: Read the exact `return NextResponse.json(...)` line in the route handler before writing UI fetch code.
  - **Prevention**: Before writing any fetch call in a page, **read the corresponding API route handler** to confirm the exact response shape. Never assume `{ items }`, `{ data }`, or `{ <resourceName> }`. Note: `ApiResponse<T>` in `src/types/index.ts` provides a shared type — use it for all route return types and the fetch caller to get type safety.
- **[2026-02-20]** Tailwind v4 `@utility container` does not reliably apply `margin-inline` or `padding-inline` — only `max-width` is honoured
  - **Symptom**: All `.container` elements flush against the left edge; devtools shows `marginLeft: 0px`, `paddingLeft: 0px` despite `@utility container { margin-inline: auto; padding-inline: 1.5rem }` being defined.
  - **Root cause**: In Tailwind v4, `@utility` declarations are placed inside `@layer utilities`. For the built-in `container` utility, `margin` and `padding` overrides are silently ignored — only `max-width` takes effect.
  - **Fix**: Keep `@utility container { max-width: 1280px }` and add plain un-layered CSS in `globals.css` (outside any `@layer`): `.container { margin-left: auto; margin-right: auto; padding-left: 1.5rem; padding-right: 1.5rem }` with responsive media queries. Un-layered CSS wins over all `@layer` declarations in the cascade.
  - **Prevention**: Never use `@utility` alone to configure container centering/padding in Tailwind v4. Always pair with un-layered CSS overrides. See `docs/design-system/01-foundations.md` Container section.
- **[2026-08-21]** The `/frontend-design` skill that `CLAUDE.md` mandates before any UI work is not shipped in this installation
  - **Symptom**: `CLAUDE.md` opens its UI section with "YOU MUST do ALL THREE… 1. Invoke the `frontend-design` skill". There is nothing to invoke.
  - **Root cause**: `.claude/commands/` holds six commands (create-feature, create-prd-tasks, review-fixes, security-review, ship, validate) and none is it. There is no `.claude/skills/` directory, no user-level `~/.claude/commands` or `~/.claude/skills`, and the installed plugin marketplace does not provide it. The string `frontend-design` appears only in `CLAUDE.md` itself.
  - **Fix**: treat `docs/design-system/*.md` as the substitute source and read them in full before writing UI, recording the reading as a dated pre-flight so the order is auditable.
  - **Prevention**: either ship the skill or amend `CLAUDE.md` to point at the DS files directly. A mandatory step that cannot be performed trains people to skip mandatory steps.
- **[2026-08-21]** Dialog corner radius is specified twice in the design system, with different values, and both cite Figma as the source
  - **Symptom**: no single answer to "what radius does a modal use", on a rule that is graded as binary.
  - **Conflict**: `01-foundations.md` radius table says `rounded-2xl` (16px) — "Modals (matches Figma dialog corners)" — and `CLAUDE.md` agrees. `04-dialogs.md` says `rounded-lg` (8px) — "per shadcn default — matches Figma" — and lists "Override the dialog content radius" under **Don't**. `00-overview.md`'s radius golden rule omits modals entirely.
  - **Fix**: `rounded-2xl` for this build, by decision recorded in the plan. `01-foundations` carries the machine-readable token manifest, whose own header declares the YAML authoritative when prose disagrees, and `04-dialogs` argues from the shadcn default — an implementation fact, not a design one.
  - **Prevention**: radius belongs in exactly one place, the `rounded:` block of the `01-foundations` manifest. Per-component docs should reference it, never restate it. `04-dialogs.md` needs correcting upstream.
- **[2026-08-21]** `DashboardNav` and `DashboardHeader` have no content slot, so an app-level control cannot be placed in the navigation chrome
  - **Symptom**: DeskLine needs an organization switcher visible on every page. There is nowhere in the shipped layout to put it.
  - **Root cause**: `DashboardNavProps` is `{ user, primaryNavItems, secondaryNavItems, iconRegistry?, brand?, settingsHref?, billingHref?, showBilling? }` and `DashboardHeaderProps` is a subset. Neither accepts `children` or any render slot. On desktop there is no horizontal header at all — only the sidebar — and `08-page-layouts.md` forbids putting anything above `PageHeader`.
  - **Wrong approach**: putting the switcher in `PageHeader`'s `action` slot. That slot is spec'd as the page's single primary CTA, which the dashboard already needs for "New ticket".
  - **Fix**: an app-owned context bar rendered by the app shell, between `DashboardHeader` and `<main>` — outside `<main>`, so the "nothing above the page header" rule still holds. No package primitive is forked.
  - **Prevention**: raise upstream — `DashboardNav`/`DashboardHeader` should accept an optional slot for tenant-level controls. Multi-tenant apps all need one, and every consumer will otherwise invent its own bar in a different place.
- **[2026-08-21]** The shipped `Badge` renders `rounded-full`, while the spec lists `rounded-lg` for badges as a binary criterion
  - **Symptom**: every badge in the app is a pill, not an 8px-cornered tag, even though nothing in app code sets a radius on one.
  - **Root cause**: the radius is baked into the package's own `badgeVariants` base classes — `"inline-flex items-center justify-center rounded-full border border-transparent px-2 py-0.5 …"` in `@upstart13-com/aiden-ui/dist/components/badge.js`. It is not a variant, not a default prop, and not overridable except by passing a competing `rounded-*` through `className`, which `cn()` would resolve in the app's favour.
  - **Conflict**: `CLAUDE.md` says "`rounded-lg` (8px) for buttons/badges". `01-foundations.md`'s radius table says `rounded-lg` — "Larger buttons, emphasis pills". The implementation says `rounded-full`. This is the same shape of divergence as the dialog-radius entry above, except here the disagreement is between the docs and the compiled component rather than between two docs.
  - **Decision — not forked.** App code sets no radius on any `Badge`. Overriding it in every call site would satisfy a grep while putting the app permanently at odds with the primitive, and would silently diverge the moment the package changed. A shipped primitive that disagrees with the spec is the package's bug to fix, not something to paper over per-call-site.
  - **Consequence to state when the radius rule is checked**: a grep of `src/` finds no badge radius at all, because the app sets none. The rendered pill comes from the package. Both facts are true and the second is not the app's to fix.
  - **Prevention**: raise upstream — either `badgeVariants` moves to `rounded-lg`, or `01-foundations.md` and `CLAUDE.md` are corrected to say `rounded-full`. Whichever way it resolves, the value belongs in one place: the `rounded:` block of the `01-foundations` manifest, with the component built from it.
