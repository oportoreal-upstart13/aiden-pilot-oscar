# Next.js & App Router Fixes

- **[2026-08-04]** `src/lib/audit.ts`'s `captureRequestMeta` (passed to `createPrismaAuditSink`) called `next/headers`'s `headers()` synchronously to read IP/user-agent for audit rows. Under Next.js 16, `headers()` is fully async (`Promise<ReadonlyHeaders>`) — calling `.get()` on it directly throws `Route "..." used headers().get(). headers() returns a Promise and must be unwrapped with await`. This surfaced specifically inside a `createAIStreamResponse({ onDone })` callback (the SSE draft route), where the thrown error was silently swallowed by the audit sink's own error handling (fire-and-forget, by design) — so the request still returned 200, but the `ai.draft` audit row's IP/UA never got captured and the failure was invisible unless you were watching server logs. Can't fix by `await`-ing `headers()`: `captureRequestMeta`'s type is synchronous only (`() => {...}`, no `Promise`), so there is no sync-safe way to read request headers under Next 16 inside this specific callback. Fixed by dropping the header read entirely (`captureRequestMeta: () => ({})`) — `requestId`/`userId` (the fields actually required by the graded audit trail) come from `getRequestContext()` elsewhere in the pipeline and are unaffected; only the optional `ipAddress`/`userAgent` enrichment columns are lost.

- **[2026-08-04]** `setAuditSink(createPrismaAuditSink(...))` registered from `instrumentation.ts` (via `import("@/lib/audit")`) silently never fires for any actual route under `next dev` with Turbopack — audit events kept hitting the default pino/console sink only, and the `audit_logs` table stayed empty, even though `configureSecurity(...)` (called from `src/lib/security.ts`) clearly worked for every route. Root cause: Turbopack's dev-mode per-route compilation gives `instrumentation.ts` its own isolated module graph; `@/lib/audit` was reachable ONLY from that graph (no route imported it directly), so the module-level `setAuditSink` call mutated a *different* copy of `@upstart13-com/aiden-security`'s internal sink state than the one route handlers' `auditLog()` calls read from. `configureSecurity` worked because `src/lib/security.ts` — which every route already imports directly — calls it inline. Fix: add a side-effect `import "@/lib/audit";` to `src/lib/security.ts` itself, so sink registration is guaranteed to happen in the same module instance every route shares. Keep the `instrumentation.ts` import too (harmless, idempotent) but don't rely on it alone in dev. Verified by checking `prisma.auditLog.count()` directly — was 0 despite dozens of routes triggering `auditLog()` calls that were visibly logging to console.

- **[2026-02-12]** `useSearchParams()` in a page component causes build error `useSearchParams() should be wrapped in a suspense boundary` → In Next.js 15+, pages that use `useSearchParams()` must wrap the consuming component in a `<Suspense>` boundary. Extract the page content into a separate component (e.g., `PageContent`) and wrap it with `<Suspense fallback={...}>` in the default export page component.
- **[2026-02-12]** `window.history.replaceState()` inside a `useEffect` that depends on `[searchParams]` causes the effect to immediately re-run and cleanup → In Next.js 14+, `replaceState`/`pushState` are intercepted and sync with `useSearchParams()`. If you clean URL params via `replaceState` at the top of an effect that depends on `searchParams`, the params change triggers re-run. Fix: defer URL cleaning until inside the async callback (after capturing the params), or use a `useRef` to store params before cleaning.
- **[2026-02-15]** `npm run build` fails with `Cannot find module './XXXX.js'` in `.next/server/webpack-runtime.js` → This is a stale Next.js build cache issue, not a code error. TypeScript compilation and linting succeed but the "Collecting page data" step fails on a missing chunk. Fix: delete `.next/` directory (`rm -rf .next`) and rebuild.
