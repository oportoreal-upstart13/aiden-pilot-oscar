# Testing Fixes

- **[2026-08-22]** No test framework can be installed in this repository, and three separate toolchain facts decide how tests must be written
  - **Symptom**: `npm install -D vitest` is not safe to run, and `node --test` on a `.test.ts` file that imports app code fails three different ways in sequence.
  - **Root cause 1 — the private registry.** There is no `.npmrc` and no `GITHUB_PAT`, while `package-lock.json` resolves every `@upstart13-com/*` package from `https://npm.pkg.github.com/download/...`, which needs auth. Any `npm install` re-reifies the tree and risks breaking a working `node_modules` for the sake of a devDependency.
  - **Root cause 2 — `server-only` is not a real package.** `node_modules/server-only` does not exist; Next aliases the bare specifier in its webpack config. So `import "server-only"` resolves during a Next build and nowhere else, and every module that opens with it (`abilities`, `org`, `tickets`, `security`, `ai-prompts`, …) is unimportable from plain Node with `ERR_MODULE_NOT_FOUND`.
  - **Root cause 3 — CJS output versus ESM-only packages.** `package.json` has no `"type": "module"`, so `tsx` compiles `.ts` to CJS. `@upstart13-com/aiden-security` (and `aiden-ai`, `aiden-realtime`) declare only an `"import"` condition, so `require()`-ing them fails with `ERR_PACKAGE_PATH_NOT_EXPORTED: No "exports" main defined`. Naming a test file `.mts` makes *that file* ESM but not its `.ts` dependencies, so the error persists one level down.
  - **Wrong approach**: mapping `server-only` to a stub in the app's `tsconfig.json`. It would make the tests import cleanly and silently point the real Next build at a no-op, disabling the guard that keeps server modules out of client bundles. A test convenience is not worth a production hole.
  - **Fix**: Node's built-in runner (`node --test`) driven by `scripts/test.mjs`, with `TSX_TSCONFIG_PATH=tsconfig.test.json` so the `server-only` stub mapping lives in a **test-only** tsconfig. The env var is set in the runner script rather than inline in the npm script because npm runs scripts through `cmd.exe` on Windows, where `VAR=x cmd` is not valid.
  - **Consequence, stated rather than hidden**: modules that import `aiden-security` cannot be unit-tested in-process. Route handlers are therefore tested **over HTTP against a production build** (`src/test/routes.test.ts`). That is stronger in most respects — nothing is stubbed, and the real `withAuth` → `parseRequest` → org-filtered query → ownership → ability chain runs in its real order — but it cannot reach a case that only arises in-process: `withAuth`'s `ctx?.params ?? {}` yielding an `undefined` id. Over HTTP, Next always supplies params. The nearest reachable proof is an id that fails the Zod bound, which shows the validator runs before any query; the `{}` branch stays covered by code review and by the D4 record, not by a test.
  - **Prevention**: if a framework ever becomes installable, Vitest would remove all three constraints at once — it resolves ESM/CJS interop, supports `resolve.alias` for `server-only` without touching the app tsconfig, and mocks modules without an experimental flag. Until then, do not add a `.test.ts` that imports anything reaching `aiden-*`; put that assertion in the HTTP suite instead.

- **[2026-08-22]** A curl cookie jar is read-only unless `-c` is passed on every request, which silently neutered a smoke probe
  - **Symptom**: probe 8 of `scripts/smoke.sh` reported "1 ticket(s) appear in both organizations" with `before=[tkt_acme_5] after=[tkt_acme_5]`. The two lists were not overlapping — they were identical, because the organization had never changed.
  - **Root cause**: the script's helpers used `curl -b "$jar"` without `-c "$jar"`. `-b` reads cookies from the jar; only `-c` writes them back. `POST /api/orgs/switch` returned 200 and sent `Set-Cookie: deskline_org=org_globex`, curl discarded it, and the follow-up list carried the old cookie. Confirmed by hand: with `-c` the jar gains `deskline_org  org_globex` and the list flips to seven Globex tickets.
  - **Fix**: pass `-c` alongside `-b` on every request in a session, not only at login. Any probe that asserts on state the server sets via cookie is otherwise asserting on nothing.
  - **Second defect found in the same probe**: the disjointness check was `a.filter(x => x && b.includes(x)).length === 0`, which passes on two *empty* sets. A disjointness assertion has to prove both sides are non-empty first, or it reports success for having tested nothing — the same non-vacuity discipline probe 10 already applies by generating foreign activity before asserting its absence.
  - **Prevention**: for any probe of the form "X does not appear in Y", assert that Y is non-empty and that X exists somewhere, before asserting the absence.

- **[2026-08-22]** A script assumed an API response shape instead of reading the route, the exact mistake `ui.md` already documents
  - **Symptom**: probe 10 reported "could not resolve the Globex agent's id".
  - **Root cause**: the script read `GET /api/me` as `.user.id`. That route returns the user flat — `{"id":"…","email":"…","name":"…","hasPassword":true,"accounts":[],"roles":[…]}` — with no `user` wrapper.
  - **Fix**: read the route's `return NextResponse.json(...)` before consuming it. `ui.md` states this rule for UI fetch code; it applies to scripts identically.
  - **Worth keeping**: the probe failed loudly instead of comparing against `undefined` and reporting PASS. A guard that refuses to run a vacuous check is doing its job, and is the reason this surfaced as a red probe rather than a green one that proved nothing.

- **[2026-09-01]** Verifying a plan by diffing only one direction cannot detect a file that was never created
  - **Symptom**: an external assessment found the app served **no security headers at all**. `src/proxy.ts` had never been created. Nothing in the repository disagreed: `npm run build` passed, `tsc --noEmit` passed, `npm run lint` passed, 40/40 tests passed, 16/16 smoke probes passed, and the plan's own verification table recorded row 7 as **PASS**.
  - **Root cause**: row 7 compared `git diff --stat` against the plan's file list by asking *which files landed that the plan did not name* — eleven, all dutifully recorded as deviations D1–D11. It never asked the inverse: *which files did the plan name that did not land*. A one-directional diff is structurally incapable of seeing an absence, so the check could only ever grow more confident the more work was done.
  - **Why nothing else caught it**: a missing middleware has no compile error, no type error, no lint error, and no failing test — every suite asserts on responses that are still perfectly valid without headers. Absence of a file is invisible to every tool that operates on the files that exist. The plan had even flagged it explicitly, in three places, one of them reading "the app currently serves no security headers" — being *written down* is not the same as being *checked*.
  - **The same hole let a second item through**: `migrations.seed` in `prisma.config.ts`, also planned, also never added, also silently absent.
  - **Fix**: run the comparison both ways. Extract every concrete path the plan names and assert each one exists, then assert every file that landed was either named or recorded as a deviation. Both directions, or neither is meaningful.
  - **A trap inside the fix**: the first attempt at the reverse check reported "ninguna" — zero missing files — and was wrong. The extraction regex used `[A-Za-z0-9._/\[\]-]` as a character class, but in POSIX ERE a backslash does not escape `]` inside a bracket expression, so the class terminated early and matched nothing. **A check that finds zero problems and a check that is broken produce the identical output.** Before believing a clean result, confirm the check's input was non-empty — here, that the path list had 45 entries and not 0.
  - **Prevention**: any verification of the form "everything planned was done" must enumerate the planned set and confirm that enumeration is non-empty before reporting on it. This is the same non-vacuity discipline as the two entries above, applied one level up — to the verification itself rather than to a probe.
